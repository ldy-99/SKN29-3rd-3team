# 00. 프로젝트 범위와 MVP 명세

## 1. 문서 목적

본 문서는 4차 청약 진단 서비스의 프로젝트 범위, MVP 기준, 사용자 흐름, 제외 범위를 정의합니다. 팀원이 기능을 구현하기 전에 “이번 프로젝트에서 반드시 끝낼 것”과 “이번 범위에서 제외할 것”을 동일하게 이해하는 것을 목표로 합니다.

| 항목 | 내용 |
|---|---|
| 통합 전 참조자료 | 기존 실행 명세, 팀 검토안, 협업 가이드를 통합 반영 |
| 적용 범위 | 서비스 목표, P0/P0.5/P1 범위, 사용자 흐름, 팀 역할 |
| 우선 독자 | PM, 프론트엔드, 백엔드, AI/FastAPI, 통합 담당자 |

## 2. 서비스 목표

4차 프로젝트는 3차 프로젝트의 청약 RAG·LangGraph 기반 진단 기능을 실제 웹 서비스 구조로 확장합니다. 사용자는 회원가입 후 자신의 청약 조건을 저장하고, 저장된 프로필과 공고 정보를 바탕으로 개인 맞춤형 청약 전략을 확인할 수 있어야 합니다.

핵심 목표는 다음과 같습니다.

| 목표 | 설명 |
|---|---|
| 사용자별 청약 프로필 저장 | 청약통장, 거주, 무주택, 세대, 혼인/자녀, 소득/자산 정보를 사용자 단위로 저장합니다. |
| 개인 맞춤형 진단 | 저장된 프로필과 공고 입력을 기반으로 추천 공급유형, 누락 항목, 판단 근거를 제공합니다. |
| 결과 저장과 재조회 | 사용자가 이전 진단 결과를 다시 확인할 수 있도록 전략 결과를 저장합니다. |
| FAQ 챗봇 연결 | 기존 RAG 챗봇을 React 화면에서 사용할 수 있도록 Django proxy를 둡니다. |
| 배포 가능한 웹 구조 | React, Django DRF, FastAPI/AI 모듈을 연결하고 Docker/Compose 기반 재현 흐름을 갖춥니다. |

## 3. P0 MVP 범위

P0는 10영업일 안에 반드시 완료해야 하는 최소 기능입니다. 기능을 늘리기보다 가입, 프로필 저장, 진단 실행, 결과 저장, 챗봇 연결, 배포 확인까지 이어지는 한 줄의 사용자 흐름을 완성하는 것을 우선합니다.

| P0 기능 | 완료 기준 |
|---|---|
| 회원가입·로그인·로그아웃 | Django session cookie 기반 인증이 동작합니다. |
| 내 프로필 조회·저장·수정 | `GET/PUT/PATCH /api/user/profile`이 동작하고 사용자별 소유권이 보장됩니다. |
| 청약 진단 실행 | `POST /api/strategy`가 저장된 프로필과 공고 입력을 사용해 진단을 실행합니다. |
| 전략 결과 목록·상세 조회 | `GET /api/strategy/me`, `GET /api/strategy/{strategy_id}`가 동작합니다. |
| FAQ 챗봇 | React에서 질문을 보내고 Django를 통해 기존 FastAPI/RAG 챗봇 응답을 받습니다. |
| PDF 공고 분석 및 수동 fallback | `POST /api/pdf/analyze`를 P0로 포함하고, PDF가 없거나 분석이 실패하면 수동 공고 입력 fallback을 유지합니다. |
| 최소 배포·검증 | 새 clone 기준 Docker/Compose 실행 방법과 수동 검증 기록을 확보합니다. |

## 4. P0.5 및 P1 범위

| 구분 | 내용 | 처리 기준 |
|---|---|---|
| P0.5 | PDF 분석 UX 고도화, 결과 UI 개선, 추가 공급유형 일부 반영 | P0가 안정화된 뒤 착수합니다. |
| P1 | 마이페이지 고도화, 챗봇 이력 저장, 공고 자동 수집, 고급 통계, 추천 설명 고도화 | 2주 MVP 범위 밖으로 둡니다. |
| 제외 | 모든 특별공급 예외 완전 반영, 운영 수준 모니터링, 대규모 크롤링, 완전 자동 공고 수집 | 이번 프로젝트의 완료 조건으로 삼지 않습니다. |

## 5. 핵심 사용자 흐름

```text
회원가입/로그인
  → 사용자 프로필 입력 및 저장
  → 기본 청약 진단 실행
  → 추천 공급유형과 부족한 정보 확인
  → 필요 시 PDF 공고 분석 또는 수동 공고 입력
  → 공고 기반 전략 결과 생성
  → 결과 저장 및 재조회
  → FAQ 챗봇으로 추가 질문
```

## 6. 입력 UX 원칙

사용자에게 모든 정보를 한 번에 요구하지 않습니다. 기본 진단은 짧게 시작하고, 특정 공급유형 판단에 필요한 값은 결과 단계에서 추가로 확인합니다.

| 단계 | 입력 범위 | 결과 |
|---|---|---|
| 1단계 기본 진단 | P0 공통 필수 필드 | 추천 공급유형, 부족한 정보 요약 |
| 2단계 정밀 진단 | 추천 공급유형별 추가 질문 | 공급유형별 `CALCULATED` 또는 `PARTIAL` |
| 3단계 공고 기반 보정 | PDF 분석 결과 또는 수동 입력값 확인 | 지역, 면적, 세대수, 가격, 일정 반영 |

## 7. 역할과 결정권

| 역할                          | 주 책임                                        | 최종 결정권              |
| --------------------------- | ------------------------------------------- | ------------------- |
| 은진: PM + React              | 제품 범위, 화면 흐름, 사용자 수용 기준                     | 제품 범위·UX 수용 기준      |
| 준억: Tech Lead + Integration | API 계약, 통합, PR, CI, 배포, 문서 취합               | 기술 계약·통합 Gate       |
| 동윤: Django                  | 세션 인증, PostgreSQL, 공개 API, 사용자 소유권          | Django 공개 API·DB 구현 |
| 지훈: AI/FastAPI              | 기존 LangGraph/RAG 재사용, 내부 AI API, adapter 검증 | AI 실행 방식·계산 로직      |

## 8. 킥오프 확정 사항

| 항목 | 확정 기준 |
|---|---|
| P0 범위 | 가입 → 프로필 저장 → PDF 분석 또는 수동 공고 입력 → 진단 실행 → 결과 저장/조회 → 챗봇 질문 흐름을 유지합니다. |
| 제외 범위 | 대규모 크롤링, 완전 자동 공고 수집, 모든 특공 예외 완전 반영은 제외합니다. |
| API 버전 | MVP에서는 `/api/...`를 사용합니다. |
| 계정 삭제 정책 | `DELETE /api/auth`는 소프트 삭제로 구현합니다. |
| PDF fallback | PDF 분석 실패 또는 PDF 미보유 시 수동 공고 입력을 유지합니다. |
| 챗봇 연결 | React는 Django proxy만 호출하고, Django가 FastAPI/RAG를 내부 호출합니다. |
| 결과 저장 단위 | 진단 실행마다 전체 strategy result와 입력 snapshot을 저장합니다. |
| ChromaDB 준비 방식 | Git에는 포함하지 않고 재빌드 방식으로 준비합니다. |
| 배포 재현 기준 | Docker/Compose 기준으로 새 clone 실행 흐름을 확보합니다. |

## 9. 최종 기준

P0 범위는 “가입 → 프로필 저장 → 진단 실행 → 결과 저장/조회 → 챗봇 질문” 흐름이 끊기지 않는 상태입니다. 기능 추가보다 이 흐름의 안정성과 팀 간 계약 일치를 우선합니다.
