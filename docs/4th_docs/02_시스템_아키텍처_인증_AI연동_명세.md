# 02. 시스템 아키텍처·인증·AI 연동 명세

## 1. 문서 목적

본 문서는 4차 프로젝트의 기술 구조, 인증 정책, React-Django-FastAPI 연결 방식, 기존 AI/RAG/LangGraph 재사용 기준을 정의합니다.

| 항목 | 내용 |
|---|---|
| 통합 전 참조자료 | 기존 실행 명세, 인증·CSRF 정책, API 계약, Day1-2 착수 문서를 통합 반영 |
| 적용 범위 | 시스템 구조, 인증, API 경계, AI 내부 호출, RAG 준비 |
| 우선 독자 | Django, FastAPI/AI, 통합, 배포 담당자 |

## 2. 전체 구조

```text
Browser
  → React + TypeScript
  → Django DRF Public API
  → PostgreSQL
  → FastAPI Internal AI API
  → LangGraph / RAG / ChromaDB
```

| 계층 | 책임 |
|---|---|
| React | 화면, 사용자 입력, 결과 표시, 챗봇 UI |
| Django DRF | 인증, 세션, CSRF, 사용자별 DB 저장, 공개 API |
| PostgreSQL | 사용자, 프로필, 진단 결과, PDF 분석 결과 저장 |
| FastAPI | 기존 3차 AI/LangGraph 기능을 내부 API로 제공 |
| LangGraph/RAG | 청약 계산, 공고 구조화, RAG 챗봇, 전략 설명 |

FastAPI는 브라우저에 직접 공개하지 않습니다. 브라우저는 Django API만 호출하고, Django가 내부 네트워크에서 FastAPI를 호출합니다.

## 3. 인증 정책

MVP에서는 Django session cookie 인증을 사용합니다. JWT는 사용하지 않습니다.

| 항목 | 기준 |
|---|---|
| 인증 방식 | Django session cookie |
| 로그인 | `POST /api/auth/login` |
| 로그아웃 | `POST /api/auth/logout` |
| 현재 사용자 | `GET /api/auth/me` |
| 계정 삭제 | `DELETE /api/auth`, 소프트 삭제 |
| React 요청 | `credentials: "include"` 사용 |

## 4. Cookie 정책

| 설정 | 기준 | 설명 |
|---|---|---|
| `SESSION_COOKIE_HTTPONLY` | `True` | JavaScript에서 세션 쿠키 접근을 차단합니다. |
| `SESSION_COOKIE_SECURE` | 운영 `True` | HTTPS에서만 쿠키를 보냅니다. |
| `CSRF_COOKIE_SECURE` | 운영 `True` | HTTPS에서만 CSRF 쿠키를 보냅니다. |
| `SESSION_COOKIE_SAMESITE` | `Lax` | 일반 로그인 흐름을 유지하면서 CSRF 위험을 줄입니다. |

로컬 개발환경이 `http://localhost`라면 개발 설정에서 Secure 옵션을 임시로 끌 수 있습니다. 운영 배포에서는 반드시 켭니다.

## 5. CSRF 정책

Django session cookie 인증을 사용하므로 CSRF 방어가 필요합니다. React는 Django가 발급한 CSRF 토큰을 포함해 상태 변경 요청을 보냅니다.

| 요청 유형 | CSRF 필요 여부 |
|---|---|
| `GET` 조회 요청 | 보통 불필요 |
| `POST/PUT/PATCH/DELETE` | 필요 |

React fetch 기준:

```javascript
fetch("/api/user/profile", {
  method: "PATCH",
  credentials: "include",
  headers: {
    "Content-Type": "application/json",
    "X-CSRFToken": csrfToken
  },
  body: JSON.stringify(payload)
})
```

## 6. 같은 도메인 서비스 구조

운영에서는 Nginx를 통해 React와 Django를 같은 도메인에서 서비스하는 구성을 권장합니다.

```text
https://service-domain/
  /              → React 정적 파일
  /api/...       → Django DRF
  내부 네트워크   → FastAPI
```

이 구조는 쿠키·CSRF·CORS 설정을 단순하게 유지합니다.

## 8. AI 실행 방식

FastAPI 실행 방식은 HTTP 호출로 확정합니다. Django는 내부 URL을 통해 FastAPI를 호출하며, local import wrapper는 P0 기본 경로로 사용하지 않습니다.

| 방식 | 장점 | 주의점 |
|---|---|---|
| HTTP 호출 | 서비스 경계가 명확하고 배포 구조와 유사합니다. | 로컬 실행과 네트워크 오류 처리가 필요합니다. |
| local import wrapper | 빠르게 연결할 수 있습니다. | P0 기본 경로에서는 제외합니다. 경계가 흐려지고 import side effect를 조심해야 합니다. |

HTTP 호출 유지 기준:

1. 기존 LangGraph가 안정적으로 실행되는가
2. 동시 요청과 세션 상태가 안전한가
3. 배포 시 구조가 단순한가
4. 테스트 fixture로 재현 가능한가

## 9. AI/RAG 연결 범위

| 기능 | P0 기준 |
|---|---|
| 자가진단 계산 | 기존 계산 로직 재사용, adapter에서 필드 변환 |
| 공고 구조화 | P0는 PDF 분석 결과를 기본으로 구조화하고, 실패·미보유 시 수동 입력 fallback을 구조화 |
| 전략 생성 | 기존 Node 흐름 재사용, 실패 시 부분 결과 반환 |
| FAQ 챗봇 | 기존 RAG 챗봇을 Django proxy로 연결 |
| ChromaDB | Git에는 포함하지 않고 재빌드 방식으로 준비 |

### 9.1 챗봇 proxy 기준

챗봇의 공개 API와 내부 AI API는 분리합니다.

```text
React
  → POST /api/chatbot
  → Django 인증/권한 확인
  → FastAPI HTTP 내부 챗봇 호출
  → Django가 공통 응답 envelope로 정리
  → React 반환
```

공개 API 요청 payload는 다음 기준으로 고정합니다.

```json
{
  "question": "청약통장 가입일은 왜 필요한가요?",
  "session_id": null
}
```

기존 FastAPI/RAG 구현이 `/api/chat`과 `question/session_id`를 사용하더라도, React에는 `/api/chatbot`만 공개합니다. Django proxy는 내부 호출 결과를 `{ data: { answer, sources, session_id }, error, request_id }` 형태로 정리합니다.

## 11. 내부 API 원칙

| 원칙 | 설명 |
|---|---|
| FastAPI는 내부망 전용 | 브라우저가 FastAPI를 직접 호출하지 않습니다. |
| Django가 사용자 권한을 검증 | FastAPI는 사용자 인증을 직접 처리하지 않습니다. |
| adapter에서 계약 변환 | 공개 API 필드와 3차 내부 필드 차이는 한 곳에서 변환합니다. |
| 실패를 구조화 | AI 실패는 500만 반환하지 않고, 가능한 부분 결과와 오류 코드를 반환합니다. |
