## 4. Day 3 전 확정하면 좋은 항목

아래 항목은 Day 3 개발 착수 전에 정리되면 충돌이 줄어듭니다. 단, P0 계약 확정보다 우선하지 않습니다.

| ID | 결정 주제 | 기본 권장안 | 선택지 | 영향 |
|---|---|---|---|---|
| D12 | 계정 삭제 정책 | MVP에서는 `DELETE /api/auth`를 계정 삭제 용도로 정의하고 실제 삭제 방식은 팀 결정 후 구현 | 소프트 삭제 / 하드 삭제 | DB 모델, 개인정보 처리 |
| D13 | PDF 분석 실패 시 fallback | 수동 공고 입력을 항상 허용 | 수동 입력 유지 / PDF만 허용 | 진단 흐름 안정성 |
| D14 | 챗봇 proxy 계약 | React는 Django만 호출하고 Django가 FastAPI/RAG를 호출 | Django proxy / React 직접 FastAPI 호출 | 보안, CORS, 배포 |
| D15 | 인증·CSRF 로컬 설정 | 운영은 Secure=True, 로컬은 개발 설정으로 분리 | 환경별 분리 / 단일 설정 | 로그인 안정성 |
| D16 | 결과 저장 단위 | 진단 실행마다 strategy result를 저장 | 전체 저장 / 최근 결과만 저장 | 마이페이지, 결과 재조회 |

## 5. P0 안정화 후 결정할 항목

아래 항목은 P0 흐름이 안정화된 뒤 결정합니다. Day 1~2 회의에서는 “지금 하지 않는다”는 합의만 있어도 충분합니다.

| ID | 항목 | 현재 기준 | 후속 결정 |
|---|---|---|---|
| L1 | PDF 확정 API | `POST /api/pdf/analyze` 우선 | `POST /api/pdf/{id}/confirm` 추가 여부 |
| L2 | PDF 분석 결과 확인 화면 | P0 최소 확인 흐름 포함, 고도화는 P0.5 후보 | 사용자가 추출값을 수정·확정하는 UI 범위 |
| L3 | 추가 특별공급 확대 | P0에서는 핵심 특공 중심 | 신생아, 노부모, 기관추천 등 추가 반영 범위 |
| L4 | 공고 자동 수집 | 이번 P0 제외 | 청약홈·마이홈 수집 방식과 법적·운영 범위 |
| L5 | 챗봇 이력 저장 | P1 후보 | 사용자별 대화 저장 여부와 보관 정책 |

## 6. 회의 중 확인 질문

회의에서 길게 논의하기보다 아래 질문에 답을 채우는 방식으로 진행합니다.

| 질문 | 확인할 내용 |
|---|---|
| P0에서 반드시 시연해야 하는 한 줄 흐름은 무엇인가? | 회원가입, 프로필 저장, 진단, 결과 조회, 챗봇 중 제외 가능한 항목이 있는지 확인합니다. |
| 사용자가 처음 입력해야 하는 필드는 과도하지 않은가? | P0 공통 필드와 조건부 필드를 분리해 입력 부담을 줄입니다. |
| FastAPI는 서비스로 띄울 것인가, 내부 import로 연결할 것인가? | 개발 속도와 배포 구조 중 무엇을 우선할지 결정합니다. |
| ChromaDB는 어떻게 준비할 것인가? | 재빌드, artifact, smoke test 축소 중 하나를 고릅니다. |
| PDF가 늦어지면 서비스 흐름이 막히는가? | 수동 공고 입력 fallback을 유지해 P0 진단 흐름을 보장합니다. |
| 계약 변경은 어디에 기록할 것인가? | API·필드·DB·환경변수 변경은 계약 문서와 PR에 함께 남깁니다. |
